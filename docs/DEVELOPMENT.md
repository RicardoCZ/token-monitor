# 开发与协作规范

> 原 `开发规范.md` 合并为本文件。环境变量与安全检查命令见 [OPERATIONS.md](./OPERATIONS.md)。

## UI 文案一致性

### 页面入口命名

- 同一功能的入口按钮名称必须一致。
- 例如：「设置凭证」页面，所有入口都叫「🔧 设置凭证」。

### 命名对照表

| 页面 | 入口名称 | 文件 |
|------|---------|------|
| 凭证设置 | 🔧 设置凭证 | `setup.html` |
| 账号管理 | 🧾 账号管理 | `accounts.html` |
| 管理后台 | ⚙️ 管理后台 | `admin.html` |

### 命名原则

1. 动词 + 名词结构（如「设置凭证」「账号管理」）。
2. 可加 emoji 前缀，保持风格统一。
3. 修改入口名称时，需同步修改所有相关入口。

## 开发实践规则（2026-04-01）

### 权限与页面职责

- 用户资源（如账号、告警规则）应放在普通用户可访问页面，不应绑在管理员页面。
- 管理员页面聚焦管理员能力（邀请码、API Key 等），避免角色混用。
- 页面权限与 API 权限必须一致，避免“接口可用但页面不可达”。

### 接口返回约定

- 前端依赖的关键字段必须由后端显式返回（如 `usage.metric_defs`），不要假设前端可自行推断。
- 统一维护字段别名映射规则，明确“存储 key”与“展示/配置 key”的转换方向。
- 对可能为空的数据返回稳定结构（空数组、默认对象），减少前端分支和空指针风险。

### 前端交互一致性

- 顶部导航统一使用同一套样式与结构（用户名 + 设置凭证 + 账号管理 + 管理后台(按角色) + 退出）。
- 列表操作优先使用页面内交互（行内编辑、内嵌表单），减少浏览器原生 `prompt`。
- 关键管理功能（如告警）优先做成独立卡片并提供账号选择器，避免隐藏流程。

### 告警规则管理

- 规则列表应支持行内编辑（阈值、冷却、启用状态）并单行确认保存。
- 保存后统一执行局部刷新，保证规则区和事件区状态一致。
- 指标键输入优先使用下拉选择，选项来源于 `metric_defs`，无可用指标时给出明确提示。

### 稳定性与排错

- 在渲染链路中使用到的工具函数（如 `escapeHtml`）必须就近定义并可用，避免静默脚本中断。
- 每次改动后至少做一次语法/构建校验（如 `py_compile`、前端 build）。
- 对“默认隐藏”的核心模块谨慎处理，优先默认可见 + 引导文案，降低可发现性问题。

## 近期经验沉淀（2026-04-02）

### 页面刷新与缓存策略

- 优先“局部刷新”，避免整页重载；切换筛选/分页时只更新目标列表。
- 刷新过程中不要先把容器清空成“加载中”，否则会产生明显闪烁。
- 监控页支持“先渲染缓存，再后台刷新”：缓存用于首屏体验，网络结果用于最终一致性。
- 自动刷新、手动刷新、返回页面恢复三条链路要复用同一套渲染函数，避免分叉行为。

### 列表布局与交互一致性

- 列表模块统一结构：`标题 -> 内容区 -> 分页区`，除非明确需求，不使用 sticky/fixed。
- 任何新布局改动先做“滚动行为验证”（页面滚动、容器滚动、分页按钮位置）。
- 用户反馈“体验怪异”时，优先回退到稳定简单布局，再做小步优化。
- 分页切换必须保持标题稳定，不改变视口焦点位置。

### 表单与控件规范

- 同一区域输入控件高度、padding、边框、圆角统一（输入框/自定义下拉/按钮对齐）。
- 优先使用页面风格控件，弱化浏览器原生样式差异（特别是 `select`、`number` 输入）。
- 自定义下拉必须保留隐藏原字段并同步 `change` 事件，确保业务逻辑零改动。
- 默认值策略要明确：可推断时直接给默认值（如保存规则默认启用），减少无效操作。

### 文案与状态提示

- 提示文案只保留“对操作有帮助”的信息，避免重复或噪声信息（如冗余账号提示）。
- 状态说明保持“颜色/状态/含义”一一对应，并统一在列表附近展示。
- “空状态 / 加载状态 / 错误状态”用词统一，避免同义多版本并存。

### 变更控制与回滚

- 每次 UI 改动都应可快速回滚到“上一个稳定布局”（CSS 与 HTML 结构尽量解耦）。
- 对高风险交互改造（下拉、分页、刷新）先单点替换，再扩展到全页面。
- 发生争议时优先保留可用性和稳定性，再迭代视觉细节。

### 前端回归最小清单（新增）

- [ ] 切换账号/筛选/分页时页面无整块闪烁。
- [ ] 列表区域结构一致：标题、内容、分页顺序正确。
- [ ] 输入框与按钮视觉对齐（高度、间距、边框风格一致）。
- [ ] 自定义下拉值与隐藏字段一致，`change` 事件仍触发原逻辑。
- [ ] 返回监控页可先显示缓存，随后自动刷新为最新数据。

## 安全基线规范（2026-04-04 新增）

### 目的

- 记录当前项目已确认的依赖漏洞项。
- 明确最低安全版本，避免依赖回退到高风险区间。

### 已确认漏洞与最低安全版本

#### 后端 Python 依赖

| 组件 | 风险说明（简） | 最低安全版本（要求） |
|---|---|---|
| `pydantic` | 低版本存在安全风险窗口 | `>=2.4.0` |
| `aiomysql` | 低版本存在已知漏洞窗口 | `>=0.3.0` |
| `python-jose` | JWT/JWE 相关历史漏洞窗口 | `>=3.5.0` |
| `python-multipart` | 低版本 DoS 风险窗口 | `>=0.0.18` |
| `cryptography` | 低版本存在已知漏洞窗口 | `>=46.0.5` |
| `requests` | `2.31.0` 存在安全风险 | 已移除（如需使用，必须为安全版本） |

#### 移动端 Node 依赖

| 组件 | 风险说明（简） | 最低安全版本（要求） |
|---|---|---|
| `@xmldom/xmldom` | XML 注入高危（GHSA-wh4c-j3r5-mjhp） | `>=0.8.12` |

说明：该依赖为传递依赖，必须通过 `mobile-app/package.json` 的 `overrides` 强制锁定，不允许移除该覆盖规则。

#### 运行环境（系统 OpenSSL）

| 组件 | 当前基线 | 策略 |
|---|---|---|
| `openssl` / `libssl3` | `3.0.2-0ubuntu1.21`（Ubuntu jammy 安全补丁回移包） | 保持系统安全更新，不强制主版本号升级 |

说明：Ubuntu LTS 使用补丁回移机制，版本号可能较低但已包含安全修复，以发行版安全仓库为准。

### 强制执行规则

- 禁止将以下版本（或更低风险区间）引入仓库：
  - `pydantic < 2.4.0`
  - `aiomysql < 0.3.0`
  - `python-jose < 3.5.0`
  - `python-multipart < 0.0.18`
  - `cryptography < 46.0.5`
  - `@xmldom/xmldom < 0.8.12`
- 禁止恢复 `requests==2.31.0`。
- 修改依赖后必须执行一次安全检查并记录结果。

## Alice 专属开发协作规范（2026-04-01 新增）

> ⚠️ **此规范仅限爱丽丝（Alice）遵循，Cursor 可以不遵循。**
> 这是爱丽丝在多次犯错后总结的规范，用来约束爱丽丝的行为，确保爱丽丝在协作过程中不再犯同样的错误。

### 发送任务前的检查清单

| 检查项 | 错误做法 | 正确做法 |
|--------|----------|---------|
| 项目名称 | 假设是某个项目 | 明确知道是 Token Monitor |
| 项目路径 | 不知道 | `~/share/new/` |
| 前端文件 | 不知道 | 明确知道具体文件路径 |
| 后端文件 | 不知道 | 明确知道具体文件路径 |

**如果不确定项目信息，必须先问主人，不能假设！**

### 验证规范（最重要！）

❌ **错误验证**（流于形式）：
- 只检查代码有没有改动（git diff）
- 不实际测试 API 是否工作

✅ **正确验证**（必须实际测试）：

1. **实际测试 API 是否工作**
   ```bash
   # 先读 backend/.env 的 PORT（默认 5188），将下面 <PORT> 替换为实际端口
   curl -s "http://127.0.0.1:<PORT>/api/accounts/<ACCOUNT_ID>/alerts" \
     -H "Authorization: Bearer <TOKEN>"
   ```

2. **检查后端服务是否需要重启**
   - 代码改了 ≠ 服务加载了新代码
   - 如果 API 返回 404，检查是否需要重启服务

3. **检查 API 是否需要认证**
   - 如果返回 "Not authenticated"，说明接口已注册，需要登录态

4. **检查端口是否正确**
   - Token Monitor 监听端口以 **`backend/.env` 的 `PORT`** 为准（详见 [OPERATIONS.md](./OPERATIONS.md#4-环境变量完整表)）
   - 不要用他人机器或旧文档里的固定端口冒充本机端口

### 验证检查清单

**每次 Cursor 说完成后，必须执行以下验证**：

```bash
# 1. 确认后端服务进程
ps aux | grep uvicorn

# 2. 测试 API（将 <PORT> / <ACCOUNT_ID> / <TOKEN> 换成实际值）
curl -s "http://127.0.0.1:<PORT>/api/accounts/<ACCOUNT_ID>/alerts" \
  -H "Authorization: Bearer <TOKEN>"

# 3. 如果返回 404，检查后端日志
tail -30 /tmp/backend.log

# 4. 如果需要重启，询问主人
```

### 验证失败的处理

**如果验证失败（API 返回 404 等）**：

- ❌ 不能假装验证通过
- ❌ 不能只汇报"代码已修改"
- ✅ 必须汇报："API 返回 404，需要重启后端服务"并询问主人

### 常见错误对照表

| 错误 | 原因 | 教训 |
|------|------|------|
| 不知道项目名称就发任务 | 没有确认项目信息 | 发送前必须确认项目路径和名称 |
| 分句发送导致 Cursor 只处理第一句 | 违反"一次性发送"原则 | 必须一次性发送完整内容 |
| 发送后立即发 Enter，内容被截断 | 没有等待 1-2 秒 | 必须等待 1-2 秒再发 Enter |
| 验证只检查 git diff，不测试 API | 验证流于形式 | 必须实际测试 API 是否工作 |
| API 返回 404 但不处理 | 没有检查后端服务状态 | 验证时必须检查服务是否需要重启 |
| 用错误端口测试 API | 没有确认端口 | 先读 `backend/.env` 的 `PORT` 再 curl |

### 核心原则

> **验证必须包括实际测试，不能只检查代码有没有改动！**
>
> **验证不是形式主义，必须实际验证功能是否工作！**
>
> **如果不确定项目信息，必须先问主人，不能假设！**
