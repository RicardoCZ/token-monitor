# Architecture Decisions

## ADR-001: 历史数据单轨改造
- 日期：2026-03-31
- 决策：历史事实源统一为 `usage_snapshots`，不再读写 `usage_history`
- 原因：
  - 多供应商指标需要 `metric_key` 维度
  - 需要保留原始/归一化载荷便于追溯
  - 减少双写与兼容分支，降低复杂度
- 影响：
  - 历史接口统一返回 `source/pagination/filters/items`
  - 旧链路逻辑已移除

## ADR-002: 自动采集与手动同步复用同一采集主逻辑
- 日期：2026-03-31
- 决策：`/api/accounts/{id}/sync` 与后台调度统一走 `collect_account_usage`
- 原因：
  - 避免业务逻辑分叉
  - 失败处理、重试、落库行为一致
- 影响：
  - 自动采集可无缝继承手动链路能力

## ADR-003: 告警评估基于最新快照
- 日期：2026-03-31
- 决策：按 `account_id + metric_key` 规则，从最新 `usage_snapshots` 评估阈值
- 原因：
  - 与单轨历史模型一致
  - 可按指标细粒度配置阈值
- 影响：
  - 新增告警事件流 `alert_events`
  - 支持冷却防抖与恢复事件

## ADR-004: 测试框架与项目代码隔离
- 日期：2026-03-31
- 决策：测试代码放在 `~/share/test-framework`，不放在项目仓库
- 原因：
  - 测试资产可跨项目复用
  - 保持业务仓库简洁
- 影响：
  - 回归需在独立目录执行 pytest

## ADR-005: 历史趋势仅独立页面
- 日期：2026-04-04
- 决策：用量趋势图只放在 `history.html`；`api.html`（实时监控）不内嵌 ECharts/历史曲线
- 原因：
  - 监控页维持单一职责与较小脚本体积
  - 历史页已具备完整交互（双轴、窗口、覆盖率），避免重复维护两套图表
- 影响：
  - P3-2 模块化范围收缩为「拆分 `api.html` 仪表盘脚本」，不包含「嵌入趋势」
  - 用户在监控页通过顶部导航进入历史趋势
  - 运维/回归单一文档：`docs/OPERATIONS.md`
